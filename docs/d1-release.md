# הכנת D1 ופרסום ה־Worker

## מה נשמר והיכן

קובצי הנכסים, המפה, הראיות והתעריפים נארזים בתוך ה־Worker ונמסרים לאחר אימות. חשבונות, אורחים, הפעלות, פרויקטים, משוב, נתוני סנכרון וייבוא משתמשים באותו binding קיים בשם `DB`. שדות שהיישום מסמן כשמורים בדפדפן ממשיכים להשתמש באחסון המקומי. מעבר לדומיין חדש אינו מעביר את נתוני הדפדפן. אין לפרסם את המאגר או את תיקיית `web/` לציבור. הרשאות ה־Worker אינן מגינות על עותק קוד או על קבצים שמוגשים מאתר סטטי.

| סביבה | הפעלה | מסד והרשאות |
| --- | --- | --- |
| פיתוח | Node 24, ‏`npm ci`, ‏`npm run build`, ‏`npm run dev` | בהפעלה ראשונה נוצר קובץ JSON פרטי עם סודות אקראיים בשם `.dev.vars` וקודי ההקמה מוצגים במסוף המקומי. אם קיים מסד קודם, נדרש קובץ הסודות המקורי שלו. המסד המקומי נשמר ב־`.preview/auth.db`. ההתחברות הרגילה נדרשת. זמין על 127.0.0.1 בלבד. |
| בדיקה והדגמה | אחרי בנייה, ‏`npm test` או ‏`npm run demo` | להדגמה מוסד סינתטי יחיד, מסד בזיכרון, סודות אקראיים בכל הפעלה ופורט נפרד, 4174. המסוף המקומי מציג קוד הקמה ו־PIN זמניים. מקימים מנהל כדי להפעיל את כניסת האורח. סנכרון מקורות חיצוני מנוטרל בהדגמה. |
| האתר הקיים ב־Sites | תוצר ייעודי `dist/server/index.js` | משתמש ב־D1 ובזהות של שער Sites. הפקודות המקומיות ותהליך GitHub אינם מפרסמים לאתר זה. |
| Cloudflare Production עתידי | ‏`dist/cloudflare/worker.mjs`, באמצעות GitHub Actions | Worker עם מסד יחיד וכתובת workers.dev ייעודית. נטען רק עם סביבת production, כתובת תואמת וסודות תקינים. פרמטר URL אינו בוחר סביבת נתונים או תפקיד. |

## הפעלה ראשונה בעתיד, לאחר אישור מפורש

1. בחר חשבון Cloudflare, שם Worker ייעודי, כתובת HTTPS מסוג workers.dev ומסד D1 שאישרת. תעד את שם המסד וה־UUID מול לוח הבקרה. אם יש נתונים קיימים שצריכים לעבור מ־Sites, אשר בנפרד תוכנית העברה, גיבוי ושחזור. חיבור למסד ריק לא יביא איתו משתמשים או פרויקטים מהאתר הנוכחי.
2. שמור עותק גיבוי מאומת של כל מסד קיים והוכח שניתן לשחזר את העותק בסביבה נפרדת. רשום גם את גרסת ה־Worker האחרונה התקינה. בדוק את תוכן היעד ואת היסטוריית המיגרציות לפני כל פקודת כתיבה.
3. סכמת הייחוס היא `db/schema.sql`. היסטוריית השינויים היחידה היא `drizzle/0000` עד `0004`. הן מתארות את אותם 12 לוחות ו־2 אינדקסים בעלי שם. במסד חדש וריק בלבד, אחרי אישור, צור את הקונפיגורציה כמתואר להלן והרץ עם Wrangler בגרסה המצוינת ב־workflow:

   ```sh
   npm run d1:config
   wrangler d1 migrations list "$D1_DATABASE_NAME" --remote --config wrangler.production.json
   wrangler d1 migrations apply "$D1_DATABASE_NAME" --remote --config wrangler.production.json
   ```

   הפקודה האחרונה משנה את המסד. אין להריץ גם את קובץ ה־schema וגם את המיגרציות. במסד קיים שתואם בדיוק לסכמה, ניתן לפרוס את הקוד ללא הרצת מיגרציות. אם קיימת היסטוריית Drizzle/Sites שונה מזו של Wrangler, יש לתעד וליישב את נקודת ההתחלה על עותק לפני השינוי הבא במסד. אין לסמן מיגרציות כבוצעו על סמך שמות הלוחות בלבד. במקרה של מסד חלקי או סטייה בסכמה, בדיקת הפריסה נעצרת. בירור ותיקון ייעשו תחילה בעותק עם גיבוי.
4. הכן Worker ייעודי והגדר ב־Cloudflare Secrets את `ATLAS_SESSION_KEY`, ‏`ATLAS_ACCESS_HASH` ו־`ATLAS_INITIAL_GUEST_CODE`. במסד חדש יש להגריל מפתח חתימה ארוך (לפחות 32 תווים), קוד הקמה בן 16 תווים מהטווח A–Z ו־2–9 ולשמור ב־Secret את SHA-256 שלו ב־hex באותיות קטנות. קוד האורח הראשוני מורכב מארבע ספרות. העבר את פרטי ההקמה לבעל המערכת בערוץ פרטי. במסד חשבונות קיים שמור את מפתח החתימה המקורי בדיוק. הוא משמש גם לגיבוב הסיסמאות, קודי האורח וקודי השחזור.
5. ב־GitHub הגדר Environment בשם `production`, הגבל אותו לענף `main` והגדר מאשר פריסה כשסוג החשבון תומך בכך. הגדר Environment variables בלבד עבור `WORKER_NAME`, ‏`ATLAS_ORIGIN`, ‏`D1_DATABASE_NAME`, ‏`D1_DATABASE_ID` ו־`CLOUDFLARE_ACCOUNT_ID`. שמור את `CLOUDFLARE_API_TOKEN` כ־Environment secret. צמצם את האסימון לחשבון הייעודי עם הרשאת פריסת Workers וקריאת D1. אין צורך בהרשאות DNS, GitHub Pages או הרצת מיגרציות ב־workflow.
6. ‏`npm run d1:config` יוצר קובץ מקומי מוחרג מ־Git. ‏`npm run d1:check` מבצע בדיקת קריאה בלבד באמצעות ה־API של Cloudflare. הוא מאמת זהות מסד, הגדרות הלוחות והאינדקסים, יעד ה־binding ושמות הסודות. אי־התאמה עוצרת פריסה. הערכים עצמם אינם נקראים. ודא במסוף שהכתובת שהוגדרה אכן שייכת לחשבון ול־Worker.
7. אחרי מיזוג ואישור לפרסם, בחר ב־Actions את **Worker verification and release**, את `main`, ואת האפשרות **Deploy the verified Worker**. ‏Push או PR מריצים בדיקות בלבד. אחרי אישור ידני התהליך בונה ובודק, מאמת את היעד, פורס את ה־Worker ובודק את `/health/ready` ואת החסימה של `/data.json`. אין בו יצירת מסד, איפוס, התקנת schema, הפעלת מיגרציות, עדכון סודות או העלאת נכסים ל־Pages.
8. לפני הפניית משתמשים, בדוק מנהל ואורח בדומיין החדש, שמירת פרויקט ומשוב, קריאת דאשבורד והפעלת סנכרון מורשה. בדוק שהגישה הישנה והנתונים הנדרשים זמינים. בכשל בפריסה, חזור לגרסת Worker תקינה ומאומתת באותו מסד. אין לשחזר מסד כחלק מחזרה לגרסת קוד.

## תקינות וחיבורי סנכרון

`GET /health/ready` מחזיר רק דגל זמינות או הודעת שירות כללית עם 503. הוא מבצע קריאת מטא־דאטה בלבד ובודק את כל הגדרות הסכמה, כולל האינדקס הייחודי המותנה של הסנכרון. `HEAD` מתאים לבדיקת סטטוס. הגדרות סכימה שונות, גם אם הוכנסו ידנית ונראות שקולות, מחייבות בדיקה. נקודת הבדיקה אינה עוקפת את אימות המשתמש על נתיב אחר.

ב־Sites זיהוי בעל החשבון בכלי MCP מסתמך על זהות המאומתת בידי הפלטפורמה. בפריסה חיצונית קריאה מורשית דורשת הפעלת מנהל תקפה מאותו מקור. לחיבור אוטומציה קיימת דרך שער מהימן, אפשר להגדיר בנפרד Secret אקראי בן 32 תווים לפחות בשם `ATLAS_MCP_GATEWAY_KEY`. השער חייב לאמת את זהות המשתמש, להסיר כותרות זהות והרשאה שהגיעו מהלקוח, ולהוסיף בעצמו את הזהות המאומתת ואת אסימון השער. ה־Worker בודק גם שכתובת המשתמש תואמת למנהל הקיים ב־D1. סוד השער לעולם אינו נשלח לדפדפן. תזמון קיים ב־Sites נשאר משויך לאתר המקורי עד חיבור ובדיקה נפרדים של היעד החדש.

בדיקות Node מפעילות תהליכי עבודה עם SQLite מקומי. בדיקת Wrangler מפעילה את תוצר ההפצה עצמו ב־workerd מול D1 מקומי ומריצה את המיגרציות על מסד זמני. היא אינה צורכת הרשאות Cloudflare. בדוק את תוצאות ה־workflow עבור ה־commit המיועד לפריסה.

[תיעוד המיגרציות של D1](https://developers.cloudflare.com/d1/reference/migrations/) · [פריסת Workers מ־GitHub](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)

## חיבור מקור חיצוני לקריאה

בתפריט המנהל פותחים **מקורות וסנכרון** ואז **חיבורים חיצוניים**. אפשר לשמור טיוטת API וטיוטת SQL במקביל. הסודות שייכים לסביבת השרת ומוגדרים רק כאשר יש מקור אמיתי. כל שליפה יזומה בידי מנהל ומציגה עד 100 רשומות. התוצאות מוצגות במסך זה ואינן מיובאות אוטומטית לפרויקטים או לנכסים.

| סוג | הגדרה במסך | הגדרה בשרת |
| --- | --- | --- |
| API | כתובת HTTPS ונתיב למערך רשומות ב־JSON, כגון `result.records`. למערך בשורש משאירים את הנתיב ריק. | `ATLAS_EXTERNAL_API_URL` עם הכתובת המאושרת המדויקת. אפשר לשלב פרמטרים קבועים רק בהגדרת השרת. אם נדרש Bearer מגדירים סוד `ATLAS_EXTERNAL_API_TOKEN`. |
| PostgreSQL ב־Neon | בוחרים PostgreSQL ומזינים טבלה או תצוגה, למשל `public.energy_assets`. | סוד `ATLAS_EXTERNAL_POSTGRES_URL` המכיל כתובת חיבור של משתמש קריאה ב־Neon. השליפה משתמשת בממשק SQL המקורי של הספק ב־HTTPS. |
| libSQL / Turso | בוחרים libSQL ומזינים שם טבלה או תצוגה. | `ATLAS_EXTERNAL_LIBSQL_URL` לכתובת הבסיס של המסד ו־`ATLAS_EXTERNAL_LIBSQL_TOKEN` לאסימון קריאה. המסד צריך לתמוך ב־Hrana HTTP v2. |

שינוי יעד או הסרה של סוד נכנסים לתוקף בהגדרות סביבת ההרצה. ממשק הניהול שולח רק מזהה מקור, שמות שדות ושם טבלה. לצורך פיתוח אפשר להוסיף את הגדרות המקור לקובץ JSON המקומי המוחרג `.dev.vars`. משתמשי PostgreSQL רגיל, SQL Server או MySQL יכולים לחבר את ממשק ה־API של הארגון, אם קיים.
